# voice-scripter — TTS読み上げ台本

会話録画の音声を**キャラのTTS読み上げに差し替える**ための台本を書く。

## このスキルが何を決めるのか（ここを外すと聞けたものにならない）

読み上げは話者ごとに別トラックへ合成されるが、**配置は全部が1列に直列**で、
間は **0.15秒固定**（PCシステム音が鳴っている区間だけ元の間隔を保つ）。

つまり **2人の台詞は絶対に重ならない**。台本に書いた行が書いた順に、
0.15秒ずつ空けて読み上げられ、**映像がそれに合わせて可変速で追従する**。

だから、このスキルの仕事は「どの行を重ねるか」ではない。
**直列に読み上げても会話として成立するように、ターンを組み直すこと**である。

### 合成は**文ごと**（1文＝1クリップ＝後処理の単位）

書いた `text` は「。」「！」「？」でコードが**文に割られ**、**1文ずつ別々に合成**される。
文が、話者チェック・字幕1枚・口パク・キャラの表情の単位になる。

* だから**文はきちんと終える**。「。」の無い長い1行にすると丸ごと1クリップになり、
  粒度が戻る（3文入りの行で1文だけ別人の声になっても、その文だけ直せない）。
* **1文はおよそ40字（約5秒）を目安に、60字を超えない**。超えたら意味の切れ目で
  「。」を打って2文にする。字幕も1枚40字で割れるので、長い1文は字幕とも噛み合わない。
  * 「。」を打つときは**語尾だけ整える**（「〜なんですけど、」→「〜なんですけどね。」）。
    **助詞・接続助詞で終わらせない**（§3のリスト）。語を足さない。
  * 実走の失敗: 1文で **203字（約27秒）** の台詞があり、そこだけ粒度がターン単位に
    戻っていた（2026-08-06）。
* **極端に短い文を作らない**。6字未満の文は隣の文へ自動でくっつけられる
  （材料が1秒に満たないと声質が安定しないため）。
* 文の数だけ 0.15秒の間が入る。**意味の切れ目でだけ「。」を打つ**（読点で足りる所を
  無理に文へ割らない）。

⚠️ **却下済みの設計（二度と提案しない・実装もされていない）**

* 「相槌だけ相手の声に重ねる」… `backchannel` フラグ、重ねる音量、重ねる位置の調整。
  実装して実走した結果「台詞がかぶってゴチャゴチャ」になり、ユーザーから複数回同じ指摘を
  受けて全部取り除いた。コード側に重ねるAPIはもう無い。
* 「元の会話の間をそのまま残す」… 長い沈黙は残さない。間は 0.15 秒固定。

⚠️ **やってはいけない書き方**（これをやると割り込みになり、聞けたものにならない）

* 相手が喋っている途中に反応する行を、独立した1ターンとして書く
  （「はい」「うんうん」だけの行を残す）。直列に並ぶので、**相手の文を分断する**。
  実走で175本中41本が「…この片方っていうのが」のような助詞終わりになった。
* 一方が長く話しているあいだに、もう一方の短い反応を何度も挟む。

## 入出力（ファイル経由・コンテキストに本文を載せない）

### 入力: `data/<date>/voice_tts_input.tsv`

ヘッダ行あり、各行 `idx<TAB>speaker<TAB>char<TAB>slot_s<TAB>gap_s<TAB>text`。

* **時刻順に並んでいる**（話者は交互とは限らない）。
* `text` は**カット後に残った word だけ**を繋いだもの。カット済みの内容は入っていない。
  無音1秒で機械的に切っているので、**文の途中で切れている行が普通にある**。
* `slot_s` = そのターンの実尺(秒)。`gap_s` = 次のターンまでの余白(秒)。
  **どちらも参考値**。読み上げが長くても映像側が待つので、尺に合わせて刈らない。
* ファイル末尾に **`# --- 画面テキスト(OCR) ---`** ブロックが付いていることがある。
  **固有名の正しい表記はこれを正とする**（STTの聞き取りは信用しない）。

### 出力1: `data/<date>/voice_tts_decisions.json`

```json
{"lines": [
  {"idx": 17, "text": "で、今の部分ですね。イヤホン片方だけの、片方っていうのが、片耳だけみたいな意味になっちゃってて"},
  {"idx": 18, "text": ""},
  {"idx": 19, "text": "はいはい、ありがちですね"}
]}
```

* **全行分**書く。説明文・他のキーは書かない。
* `text` を空文字にすると、そのターンは**読み上げない**。
* `backchannel` のようなフラグは**無い**。全部が同じ1列に並ぶ。

### 出力2: `data/<date>/voice_tts_terms.json`

`{"terms": [{"read": "<読み上げ文中のカタカナ>", "display": "<字幕に出す正式表記>"}, ...]}`

## 手順

1. 入力TSVを読む（末尾の画面OCRブロックも読む）。
2. **会話として通して読む**。1行ずつ独立に処理しない。誰が何の話をしていて、
   どこで話し手が代わるのかを掴む。
3. 各行を **読む / 読まない（隣へ寄せる）** に仕分ける（下記）。
4. 読む行は、**そのターンだけで言い切る台詞**に整える（下記）。
5. **書き上げた全行を見直す**（下記「最後の見直し」）。ここを飛ばすと、
   同じことを2回言う台詞や、助詞で終わる台詞がそのまま合成される。
6. `voice_tts_decisions.json` を `Write` する。
7. **用語表記の対応表** `voice_tts_terms.json` を `Write` する（下記）。

## 1. 読むか、読まないか（相槌の扱い）

全部が直列に並ぶので、**合いの手をそのまま1ターンとして残すと、相手の文が割れる**。

**単体では情報を持たない合いの手は、原則 `text` を空文字にして読まない。**

* 「はい」「はいはい」「うん」「ええ」「なるほど」「そうですね」「あー」「へー」
* 笑い声だけの行

会話のリズムとして残したいものは、**捨てるのではなく次の自分の発話の頭へ吸収する**。

```
44  mossan  はいはい
45  priya   （相手のターン）
46  mossan  片方でもギリギリいけるレベルですね
```
→ 44 を空文字にし、46 を「**はいはい。片方でもギリギリいけるレベルですね**」にする。

**独立した1ターンとして残してよい**のは、その行だけで会話が一往復するもの。

* 「あ、独自のやつですか?」← 質問。相手が答える
* 「まあ、そんなに違和感はないですよね」← 評価。相手が受ける
* 「なるほど、じゃあ無料でも使えるってことですね」← 確認。相手が肯定する

**目安**: 相手のターンに挟まる合いの手は残さない。相手が言い終わってから
自分が話し始めるところだけをターンにする。`slot_s` / `gap_s` を見て、
**そのターンが本当に相手の発話の切れ目に置けるか**を確かめる。

## 2. 割れた文を繋ぐ

入力は無音1秒で機械的に切っているので、**一続きの発話が複数行に割れている**ことがある。
同じ話者の連続する行（間に相槌しか無い場合を含む）が一続きなら、**先の行にまとめて
後の行を空文字にする**。

```
41	Taniguchi	priya	3.98	0.20	あ、で、今の部分ですね、はい、あの、イヤホン片方だけの、この片方っていうのが、
42	mossan-hoshi	yume	0.62	0.10	はいはい
43	Taniguchi	priya	2.10	0.30	要は片耳だけって意味なんですけど、
```
→ idx=41 に繋ぎ、43 を空にする。**42 の「はいはい」も空にする**（間に挟まる合いの手を
残すと、繋いだはずの文がまたそこで割れる）。

**繋いだ結果が長くなっても構わない**。読み上げが元の尺より長いときは映像側が待つ
（先行してフリーズする）ので、**尺を理由に文を切ってはいけない**。

### 繋いだら、必ず重複を落とす（ここを飛ばすと同じ話を2回する台詞になる）

割れた行は**同じ話者が言い直している**ことが多い。素直に連結すると、1つのターンの中で
同じ主張が2回・3回出てくる。実走で出た失敗:

> あれですよね。いわゆるDAWというか、**タイムラインがあって、そこで自由にトラックを
> いじるっていう機能があった**と思うんですけども、多分そこら辺用に入れたやつって
> ことですかね。**あれって結局、各トラックをばらして、いろいろいじったりできるっていう
> 機能があった**じゃないですか。それ系のやつで。**必然的にSEが欲しくなる**と思うんですよ。
> その流れで、**絶対SEが欲しくなる**と思うんですよね。

ユーザーの反応は「**冒頭に同じこと3回言ってる（SEが欲しくなる3連発）これ大丈夫？**」。
TTSの崩れではなく**台本がそう書いてあった**。

繋いだ行を書き終えたら、**そのターンを声に出して読むつもりで見直し**、
同じ内容の言い換えが2回出ていたら**後ろ側を消して1回にする**。
消すのは「言い方が弱いほう」「情報が少ないほう」。

* 「〜っていう機能があった」×2 → 具体的なほうだけ残す
* 「必然的にSEが欲しくなる」＋「絶対SEが欲しくなる」 → **1回だけ**にする
* 「〜ですかね。」「〜ってことですかね。」のような確認が連続 → 1つにまとめる

**1ターンが20秒（およそ150字）を超えたら、まず重複を疑う**。
それでも長いなら、内容が本当に多いということなので長いままでよい。

## 3. 台詞を書く

**各ターンは、そのターンだけを聞いて意味が通る台詞にする。**

### 大原則: 情報を変えない（無い要素を入れない・ある要素を消さない）

これは**この人たちが実際に喋った内容**である。**言い回し・語尾・語順の整形は自由**だが、
**情報が1つでも増減してはいけない**。

**やってよい**（情報が変わらない）:

* フィラー（えー/あのー/えっと/まあ 等）・言い直し・繰り返しを削る
* 語尾を落ち着かせる（「…なんですけど」→「…なんですけどね」）
* 語順を直す、ねじれた文を整える、明らかな聞き取り誤りを直す
* 話し言葉として自然に整える

**禁止**（情報が増える）— 実走でやってしまった例:

| 元の文字起こし | 書いてしまった台詞 | 増えた情報 |
|---|---|---|
| 「タイグさんの方ってなんかありまっかー」 | 「**今日は**そちらから、なんかありますか」 | 「今日は」＝時期の限定 |
| 「はい」 | 「はい、はい、**なるほど**」 | 理解・納得したという反応 |
| 「あははは」 | 「あはは、**確かに**」 | 同意したという反応 |
| 「まあまあ」 | 「まあまあ、**なるほどですね**」 | 同上 |

* **数字・固有名・回数・日付を補完しない**。聞き取れていないものは書かない。
* 話者が言っていない**結論・評価・要約を足さない**。
* **繋ぐときも同じ**。文を繋ぐための「で、」程度は可だが、
  «なるほど» «確かに» «そうですね» のような**反応を挿入してはいけない**（同意の有無は情報）。

⚠️ **見直しモードで「語を足す」ときも同じ**。足してよいのは、**その行または
隣接する行の文字起こしに実際にある語**だけ。無ければ足さずに、削る方向で直す。

* **意味を保つ**。要約ではなく整形。勝手に情報を足さない。
* フィラー（えー/あのー/えっと/まあ 等）・言い直し・繰り返しを除去する。
* Whisperの認識誤り（文脈上明らかな同音異義・固有名詞の誤り）を直す。
* 話し言葉として自然に。書き言葉にしすぎない（口調は元の話者のものを維持）。
* **助詞・接続助詞で終わらせない**。書き終えたら全行を検査すること。
  次で終わっていたら繋ぎ忘れか、言い切りに直し忘れ:

  > …が / …を / …に / …は / …で / …と / …も / …の / …から / …ので / …んで /
  > …けど / …けれど / …ですが / …ますが / …とか / …たり / …つつ / …ながら /
  > …して / …くて / …なくて / …ちゃって / …しまって / …という / …ように

  ただし**そこで本当に言い終えている**こともある（言いさし・尻すぼみ）。その場合は
  読み上げとして落ち着く形に整える（「…なんですけど」→「…なんですけどね」）。

### 固有名は「読み」で書く（TTSの誤読対策）

読み上げ文は **TTSが読む文字列**なので、**誤読しそうな固有名・記号はカタカナに開く**。

* 例: `Lyria 3.5` → 「リリア3.5」 / `Suno AI` → 「スノーAI」 / `GIGAZINE` → 「ギガジン」 /
  `BPM` → 「ビーピーエム」 / `npm install` → 「エヌピーエム インストール」
* **よく知られた語はそのままでよい**（`Google` / `Python` / `GitHub` / `AI` / `LLM` 等）。
  一般的な語まで開くと逆に不自然になる。開くのは**読み間違えそうなものだけ**。

## 4. 最後の見直し（書き上げてから、必ず全行を通す）

書いた直後は自分の書いた台詞が正しく見える。**一度書き終えてから、次の4点だけを
機械的に検査する**。実走で怒られたのは全部ここを飛ばしたせい。

1. **読む行だけを上から順に読み上げてみて、会話として成立しているか。**
   これが一番大事。合成では書いた順に 0.15秒ずつ空けて並ぶだけなので、
   ここで不自然なら本番でも不自然になる。次を見る:
   * **合いの手だけの行が残っていないか**（「はい」「なるほど」単独）→ 空にするか隣へ吸収
   * 同じ話者の行が続いているのに、内容が繋がっていないか → 繋ぐ
   * 相手の質問に答えていない／答えが先に来ていないか
2. **元の文字起こしに無い語が入っていないか** → §3の大原則。
   書いた行を元の `text` と1行ずつ突き合わせる。足した語が1つでもあれば消す。
3. **同じことを2回言っていないか**（繋いだ行に多い）→ 上記「繋いだら、必ず重複を落とす」
4. **助詞で終わっていないか** → 上記のリスト
5. **60字を超える1文が無いか** → 合成は文ごとなので、長い1文はそこだけ粒度が粗くなる。
   意味の切れ目で「。」を打つ（§「合成は文ごと」）。**この検査は「。」で数えること**。
   1ターンが長いかどうかではなく、**1文が長いかどうか**を見る。

そのうえで、**20秒（150字）を超えるターンだけもう一度読む**。たいてい重複が残っている。

## 5. 用語表記の対応表（`voice_tts_terms.json`）

字幕は読み上げ文から作られるので、**このままだと字幕に「リリア3.5」と出てしまう**。
そこで「読み → 字幕に出す正式表記」を書き出す。**字幕側だけが正式表記に戻る**。

* `display`（正式表記）は**画面OCRブロックを正**とする。OCRに無ければタイトル/概要欄、
  それも無ければ一般的な公式表記。**STTの聞き取りをそのまま採用しない**（表記ゆれの元）。
* 対象は上で**カタカナに開いた語すべて**。開かなかった語は書かなくてよい。
* 表記ゆれ（`Lyria3.5` / `Lyria 3.5` / `lyria`）はどれか1つに寄せる（タイトルの表記に合わせる）。
* 長い読みが先に当たるので、`リリア3.5` と `リリア` の両方を書いてよい。

```json
{"terms": [
  {"read": "リリア3.5", "display": "Lyria 3.5"},
  {"read": "リリア", "display": "Lyria"},
  {"read": "スノーAI", "display": "Suno AI"},
  {"read": "ギガジン", "display": "GIGAZINE"},
  {"read": "ビーピーエム", "display": "BPM"}
]}
```

## 見直しモード（`voice_tts_recheck.tsv` が指定されたとき）

合成した声が**参照音声と別人になった**行。シードも参照セットも振り直した後で、まだ
閾値を割っている＝**文そのものが原因**の可能性が高い。

* **入力**: `idx<TAB>char<TAB>sim<TAB>sim_min<TAB>at<TAB>text`。
  * `idx` … **`17` はターン全体、`17.1` はターン17の2文目**（0起点）。合成は文ごと。
  * `sim` … クリップ全体の話者類似度（0.85未満が対象）
  * `sim_min` … **最悪の窓**の類似度（0.80未満が対象）、`at` … その窓が始まる秒
* **出力**: `voice_tts_decisions.json` を Read して、該当 `idx` の `text` だけを
  **部分更新**して書き戻す（他の行は変えない）。
  * `17.1` のように文番号が付いていたら、**その文だけ**を直す。同じ行の他の文には
    触らない（触ると合成済みのクリップまで作り直しになる）。
  * 文の数を変えない（「。」を増減させない）。増減すると文番号がずれて、
    **直していない文まで作り直しになる**。
* **直し方**: 参照音声は**落ち着いた読み上げ**なので、そこから離れた文ほどスコアが落ちる。
  * 強い感情表現・叫び（「まじか！」「うおー」）→ 落ち着いた言い方へ（「本当ですか」）。
  * 感嘆符・連続する「！？」を減らす。語尾の伸ばし（「〜だよねぇ」）を整える。
  * 極端に短い1語だけの行は材料不足で声質が安定しない。**その行や隣の行の
    文字起こしに実際にある語**を使って2〜3語にする。**無ければ足さない**
    （§3の大原則。無い語を足すくらいなら、その行は読まない＝空文字にする）。
  * **意味は変えない**。トーンだけ落ち着かせる。
* **`at` が 0.0 付近＝出だしだけ崩れている**（Qwen3-TTS は喋り出しで参照に乗り切らない
  ことがある）。この場合は**文頭を直す**。実測では 0.80 を割った7本のうち**5本が `at 0.0`**
  で、全部が「あ、」「で、」「はい、」「うち、」のような**短い助走で始まる文**だった。
  * 文頭が「まあまあ、」「んー、」のような曖昧な音だと崩れやすい。
    はっきりした語で始める（「まあまあ、意味わかんないですね」→「意味わかんないですね」）。
  * **文頭の1〜2字＋読点を落とす**（「あ、はい、多分そうだと思いますね」→
    「多分そうだと思いますね」／「で、ビーピーエムとかは〜」→「ビーピーエムとかは〜」）。
    落とすのはフィラー・接続詞・相槌だけ＝**情報は変わらない**。
  * 文頭の感嘆・伸ばし（「あー、」「えー、」）を落とす。
* **短くしすぎない**。実測で **13字のクリップが `sim_min` 0.798** まで落ちた。
  ⚠️ **「。」を打って割った結果、15字未満の文ができるなら、そこは割らない**
  （読点のままにする）。長い1文を割るのと、短い文を作らないのは**両立させる**。
  * それでも落ちるなら、**その行を読まない**（空文字）ことも選択肢。
    助走のために文字起こしに無い語を足してはいけない。

## 注意

* `idx` は入力に存在するものだけ。創作しない。
* **台詞の中身も創作しない**（§3の大原則）。削る・繋ぐ・直すだけ。
* 出力はJSONのみ。所感や前置きをファイルに書かない。
* **合いの手だけの行を残さない**。全部が直列に並ぶので、相手の文を分断する。
* `read` は**読み上げ文に実際に書いた文字列**でなければ当たらない（単純な文字列置換）。
  読み上げ文で「スノーAI」と書いたのに `read` を「スノー AI」にすると効かない。
* 見直しモードで読み上げ文を書き換えたときは、**`voice_tts_terms.json` も見直す**
  （新しく開いた語があれば追記する）。
